# DEEP_INTERVIEW_SPOKEN_ANSWERS.md
## 0. 使用说明
本文件对应口语版面答准备稿。核心目的是将 Evidence Map 中的硬核证据、指标与故障诊断过程，转化为在技术面试中可以自然、流畅表达的第一人称回答。

背诵和准备回答时，建议遵循以下结构：

1. **直接抛出结论**：解释某个设计、指标或优化到底解决了什么核心工程问题，体现系统与架构思维。
2. **简述底层机理**：说明为什么会这样，背后的公式、数据流或工程取舍是什么，体现八股深度。
3. **结合项目事实**：绑定到具体的设计阶段、代码路径或日志指标，证明真实做过。
4. **收敛至安全边界**：用一句话大方陈述技术局限性，绝不刻意隐瞒失败或强行包装未实现的成果。

### 1.2 原理到口语速查
| 面试官热身题 | 自然口语回答 | 项目事实映射 | 安全边界（防守提示） |
| --- | --- | --- | --- |
| **模型量化的理解** | 量化的本质是用低比特整数近似浮点张量，用精度换取运行速度和内存；难点在于后处理阈值和输出分布是否依然可信。 | FastSAM INT8 的 scale 过大导致 confidence 阈值后无候选；LoRA W8A8 出现细粒度能力坍塌。 | 实事求是说明没有做 QAT，部分模型目前只降级走 FP16。 |
| **PTQ 与 QAT 区别** | PTQ 是训练后通过少量校准数据计算量化参数，怕激活异常值；QAT 在训练中模拟量化误差，保精度能力强但算力成本高。 | 我们的部署主要是 PTQ 量化诊断与 FP16 降级方案。 | 明确说明项目目前未跑通 QAT 流程。 |
| **per-tensor 与 per-channel** | per-tensor 对整个张量共用一组 scale，容易被异常值带偏；per-channel 给不同通道独立计算 scale，通常能更好地保留分类/置信度等小动态范围通道的信息。 | FastSAM 的检测头就是共用 scale 被坐标大值主导，压扁了置信度的动态范围。 | 目前没有在板端实现 per-channel 修复，主要是理论分析。 |
| **LoRA 核心原理** | LoRA 冻结预训练权重，用两个低秩矩阵的乘积去近似权重增量，极大降低了微调时的可训练参数量。 | 训练参数为 rank=32、alpha=32，冻结了视觉编码器和投影层，在 PC 仿真有效，但板端 W8A8 量化后失效。 | 承认 LoRA 在板端量化下目前处于失败状态，不包装成有效方案。 |
| **KV cache 的作用** | 自回归解码阶段需要不断关注历史 token，KV cache 通过缓存已生成的 Key 和 Value，避免了重复计算，但会占用大量运行内存。 | 它直接决定了多模态大模型的 TTFT（首字延迟）和 Decode TPS。 | 目前没有在板端做 KV cache 的底层优化。 |
| **背压（Backpressure）机制** | 上游生成比下游消费快时，如果没有背压限制，系统内存会因为任务积压而耗尽；有界队列是背压的工程载体。 | 我们的 Edge 运行时队列容量设为 4-2-4，积压时触发 drop-oldest 丢弃最旧帧，优先保障当前实时性。 | 承认有界队列只实现了协作式退出，未设计 close/drain 等高级生命周期。 |
| **转换成功是否算部署成功** | 不算。模型部署要分为导出文件、真机运行、数值一致性检验、以及任务指标可用性这四个层层递进的验收阶段。 | YOLOv8n 在 RKNN 跑通了 smoke，但数值相关性几乎为零，因此被判定为 blocked，未进主线。 | 明确说明 YOLO 最终是在 ONNX Runtime CPU 上降级运行。 |
| **结构化 JSON 解析率的意义** | json_parse_ok 只能说明模型输出符合 JSON 语法、可被后端反序列化消费，绝不能等同于模型的缺陷检测准确率。 | Qwen3-VL completions 虽然实现了 36/36 成功解析，但板端 LoRA 的细粒度缺陷识别率是 0/7。 | 不把解析成功包装为缺陷检测准确率。 |


### 1.3 项目术语正面表达
+ **CPU 降级运行（ORT CPU fallback）**：由于定位器在板端 NPU 一致性校验未通过，我们优先保障数值正确性，做出了 ONNX Runtime CPU 的降级运行决策，以此保住系统同步检测的主链路。
+ **来源标定叠加（Source-aware overlay）**：前端界面会清晰标明每一个缺陷框的推理来源，防止定位器结果、大模型候选框以及 fallback 默认框在可观测层发生混淆。
+ **核心字段保护（Canonical field guard）**：异步增强的大模型只被允许填充解释性描述（如 `observation`），绝对不允许修改定位主链路写下的缺陷类别、置信度以及坐标等核心字段。
+ **负载削减门控（Load-shedding gate）**：EfficientAD 定位为负载过滤门控，虽然 AUROC 精度不足以做最终决策，但能在大流量时过滤掉正常样本，减少慢推理线程的并发压力。
+ **二进制分段上传（Multipart upload）**：图片与元数据通过 multipart POST 协议独立传输，避免 Base64 编码带来的 33% 额外体积膨胀，同时也方便后端进行独立的契约校验。

## 3. 1 分钟项目介绍
### 3.1 端侧部署方向
> 我主要在 RK3588 平台上验证工业缺陷检测模型在边缘端的落地可行性。Edge 端采用 C++20 实现了四个解耦的任务线程：图像采集、EfficientAD 异常过滤、YOLO/VLM 推理、以及网络上传。在大模型路径的测试中，虽然基于 FastSAM 候选框与 Qwen3-VL 的多模态链路能闭环跑通，但大模型推理延迟平均在 15 秒左右，不适合做同步定位。因此，我将同步定位切到了更轻量的 YOLOv8n 定位器，在 CPU 上跑 ONNX Runtime fallback 验证，单步推理大概在 187 毫秒左右，成功跑通了长稳闭环。需要说明的是，这个耗时只包含检测模型的单步推理，不含网络上传，目前也主要是基于 ORT CPU 而非 NPU。
>
> + `[💡 内部提示：严守 C03/C18 延迟数据口径]`
>     - _187.7ms 只是 T3 模型单步推理耗时，不要将其混淆为整个流水线的端到端延迟。_
>

### 3.2 C++/系统方向
> 我负责的主要是 Edge 端的 C++ 运行时设计。系统基于 C++20 的 `std::jthread` 启动了四个固定职责的任务线程，线程之间通过三个有界队列进行数据流转。当遇到慢大模型推理导致下游积压时，队列会触发 drop-oldest 策略丢弃最旧帧，优先保障当前的实时画面。当系统需要退出时，jthread 和队列的 stop_token 可以进行协作式阻塞唤醒与安全清理，防止 RKNN/RKLLM 句柄发生内存泄露。上传线程也是完全独立的，保证网络抖动不会直接打崩前面的推理。不过作为工程验证系统，我们目前还没有实现像 close 或 drain 等更复杂的队列生命周期 API。
>
> + `[💡 内部提示：严守 C04 BoundedQueue 边界]`
>     - _不要把我们这个四线程协作退出包装成云端高可用的通用 Runtime。_
>

### 3.3 AI 模型部署方向
> 在模型部署上，我主要做的是多方案转换与端侧量化失败诊断。比如 EfficientAD 因为异常分数区分度有限，我们把它降级作为过滤慢大模型负载的门控；FastSAM 则是由于 INT8 量化后的反量化级距过大，导致置信度阈值过滤后没有候选框，我们最终 fallback 到了 FP16 模式以提取候选框；而 LoRA 在 PC 端精度表现不错，但到了板端 W8A8 量化模型后，细粒度缺陷类型的识别率彻底坍塌。这些真实的量化 cliff 诊断经历，帮助我们重新设计了系统的 fallback 降级和分层模型职责。目前 LoRA 暂时无法作为有效的端侧部署主线，主要作为失败诊断的典型案例。
>
> + `[💡 内部提示：严守 C08/C12/C17/C18 量化边界]`
>     - _大方承认 FastSAM 没实现 mask 分割（仅作候选框），LoRA 在板端处于失效状态。_
>

## 4. 3 分钟项目介绍
### 4.1 普通技术面版本
> 这个项目我是从定位、架构和排障取舍三部分来完成的。首先，项目的核心定位是基于 MVTec AD 公开数据集的 RK3588 端侧推理可行性验证，不是真实的工厂上线项目。
>
> 在架构设计上，我们采用端云分离。Edge 端是 C++20 实现的四线程流水线，包括图像采集、EfficientAD 异常过滤、YOLO/VLM 推理、以及 multipart 上传。后端基于 FastAPI，负责 API 契约和 bbox 坐标合法性校验，通过 WebSocket 把检测结果广播给 Next.js 前端进行时序数据和 Chrome Trace 性能观测。
>
> 在模型验证上，我们先走通了第一条大模型解释路径，用 EfficientAD 做异常门控，FastSAM 提取缺陷位置的候选框，再调用 Qwen3-VL 2B 模型输出结构化的缺陷描述 JSON。虽然这个大模型路径在板端长稳测试里表现很稳定，但它的平均推理延迟在 15 秒左右，不适合做同步定位。因此，我们演进出了第二条低延迟路径，用轻量级的 YOLOv8n 做同步检测定位。虽然我们尝试过 YOLO 的 RKNN 芯片部署，但由于数值一致性测试没过，分类通道相关性几乎为零，我们做出了 fallback 降级决策，目前主路径是跑在 CPU 的 ONNX Runtime fallback 模式下，单步推理平均耗时在 187.7ms 左右。
>
> 在模型排障上，我们积累了几个典型失败复盘：包括 FastSAM 量化后由于动态范围不匹配导致的置信度塌陷、LoRA 微调在大模型低比特 W8A8 量化后发生的性能坍塌，以及设备代理上报契约不一致导致的 400 报错。总的来说，我更倾向于将它定义为一个高完整度的端侧部署工程验证项目，它的价值就在于我们把部署遇到的失败和降级 fallback 决策跑成了一个完整闭环。
>
> + `[💡 内部提示：严守全局 Evidence Map 约束]`
>     - _不要把失败定位说成已彻底修复，如 5d soak 中断、MPU6500 原始日志缺失等问题需保持边界。_
>

### 4.2 大厂深挖版本
> 在做这个系统时，我面临的最核心工程决策是“如何处理大语言模型高延迟与实时检测之间的冲突”。一个容易做出来但很有隐患的设计，是让大语言模型同步主导整个硬件检测链路。我的决策是把“实时同步检测”和“异步大模型语义增强”解耦开来，让 VLM 处于旁路解释的地位。这样即使网络抖动或大模型生成变慢，底层的同步定位主链路依然能够高速稳定运行。
>
> 基于此，我们把当前的主控任务收敛到了 RK3588 板端，由 C++20 的 jthread 启动四个独立的 worker 线程，用有界队列进行背压传递。当大模型推理较慢引发积压时，队列会触发 drop-oldest 策略，优先处理最新的图像帧。
>
> 而在模型侧，我们遇到了很多端侧部署的经典落差。例如 YOLOv8n 在 PC 端转换和 smoke 测试表现不错，但经过一致性校验发现 class score channels 相关性接近零。为了保证系统的正确性，我没有硬把不准的模型推上 NPU，而是设计了 ORT CPU fallback 降级，在单机 extended soak 中跑通了 2000 多帧无崩溃，模型耗时 187.7ms。
>
> 对于多模态模型，Qwen3-VL-2B 本身跑通了 30 分钟的长稳测试。但当引入 LoRA 微调后，由于大模型 W8A8 低比特量化对细粒度 delta 权重的精度损伤，板端的分类识别率发生了崖式跌落。为了防止异步慢模型污染主链路的检测指标，我们设计了 canonical field guard 机制，强行限制大模型只能补充语义描述，无法改写 bbox 坐标和缺陷类别等核心字段。
>
> 我们在后端进行了 345 项契约测试，前端也实现了 bbox 来源隔离和 timing 观测，防止不同模型的输出被误读。这些探索也向我们证明：模型转换成功绝对不等于部署可用，我们需要对数值一致性、量化 cliff、数据契约和系统降级有非常清醒的认识。目前异步长稳 soak 测试在 5 天测试中因 blocker 中断，这说明在数据一致性上还有工作要做，它目前依然是一个极具技术参考价值的部署验证工程。
>
> + **[****💡**** 内部提示：对齐标杆-A 与标杆-B]**
>     - _回答中将“大模型量化 cliff”与“NPU 一致性失败”作为技术深度抓手，展示自己对 PTQ 反量化代数、量化参数缩放、首字延迟以及多线程同步的深刻理解。_
>

## 5. 5 分钟完整项目讲稿
大家下午好。我今天汇报的项目是基于 RK3588 平台的端云分离工业视觉 AI 部署验证系统。首先，为了工程上的严谨，我想先界定一下项目的边界：这并不是一个已经交付给客户并拥有真实产线数据的生产级项目。它是一个基于 MVTec AD 公开数据集，在板端重点验证多模型转换、端侧 C++ 运行时背压、后端契约测试以及前端可观测性的闭环可行性验证工程。

我们为什么采用端云分离设计？因为如果在 RK3588 板端承担太多诸如数据库持久化、WebSocket 连接广播、Web 服务等任务，不仅会严重压榨板端的计算资源，还会使实时检测链路很容易被网络抖动或者 UI 状态卡住。因此，我们明确划分了职责：Edge 端保持极致的简单，只做推理、背压控制和二进制分段上传；FastAPI 后端负责接收、契约校验与 SQLite 归档，并用 WebSocket 广播；Next.js 前端负责展示、复盘和 Chrome Trace 耗时定位。

首先看 Edge 端的 C++ 运行时设计。我们用 C++20 的 `std::jthread` 启动了四个固定职责的任务线程：T1 采集线程、T2 EfficientAD 异常过滤线程、T3 模型推理线程和 T4 上传线程。线程间通过三个有界队列（BoundedQueue）相连，容量分别设为 4、2、4。因为推理线程的延迟和吞吐在不同模式下差别极大，如果发生积压，队列会触发 drop-oldest 策略，丢弃掉队列头部的旧帧，优先保障当前采集到的最新图像。当系统需要安全退出时，利用 stop_token 协作取消机制唤醒阻塞在空队列上的条件变量，依次释放资源，防止内存泄露。上传线程与前面的推理分离，网络延迟不会反向卡住采集。

在推理公路上，我们重点探索了两种技术路线。

第一条是大模型异步增强链路。由 EfficientAD 作为前置门控进行异常筛选，当检测到潜在异常时，调用 FastSAM 提取缺陷位置的候选框，最后喂给轻量级的 Qwen3-VL 2B 模型进行多模态语义生成。这个复杂的双路径模型在板端做过长稳测试，实现了零崩溃和 100% 的结构化 JSON 解析。但是，这也暴露出多模态模型在边缘端的最大问题——耗时。Qwen3-VL 在板端的 TTFT（首字时间）和 decode 累计延迟平均在 15 秒左右。这种秒级的延迟决定了多模态模型根本不能充当同步的主检测器。

因此，我们演进出了第二条定位器路线。我们放弃大模型同步检测，改用定制的 YOLOv8n 定位模型进行同步检测。虽然我们尝试过 YOLO 的 rknn 芯片转换，但在真机调试时发现数值一致性出现致命偏差，NPU 导出的 class score channels 与参考 ONNX 输出的相关性几乎归零。为了保证系统的正确性，我没有为了堆砌概念将错误输出的模型强行上线，而是果断做出了 ONNX Runtime CPU 的降级运行决策，保住了系统同步主链路的数值正确性。该 CPU 路径在长稳 soak 测试中跑通了 2000 多帧，模型单步延迟稳定在 187.7 毫秒左右。

在部署的排障和诊断上，项目产出了几个非常有代表性的技术沉淀。  
第一个是 FastSAM 的 INT8 量化失败案例。PTQ 转换后我们发现 output0 置信度阈值过滤后没有候选框。通过手算反量化公式发现，它的 output0 scale 被大坐标值拉到了 2.82，由于置信度的有效动态范围本在 0 到 1 之间，一个量化级距就直接超过了整个区间，导致信息丢失。为此我们fallback到了 FP16 模式以保留正确的 proposal 框。  
第二个是 LoRA 微调在端侧低比特 W8A8 量化下的性能坍塌。PC 端仿真的细粒度 defect_type_exact 识别率在 51.8%，但到板端量化模型后识别率为 0/7。这让我们意识到大模型 W8A8 低比特量化会严重损伤微调出来的细小 delta 增量，促使我们设计了核心字段保护机制（canonical field guard），防止异步大模型改写同步 YOLO 写入的主缺陷指标。

最后在云端可观测性上，后端入口强制校验 Meta 数据的字段越界和 JPEG 大小，目前 345 项契约测试全部通过；前端 FrameInspector 可以清晰标明缺陷框的推理来源（YOLO localizer 或是 VLM proposal），ProfilePage 可以直接导出 Chrome Trace 性能日志。

回盘来看，这个项目最大的收获并不是我们跑出了多么好看的准确率指标，而是我们在端侧真正摸清了多模型混合部署时的技术局限和阻碍，完成了背压、一致性校验、NPU fallback 以及端云契约的闭环调试。这就是我对本项目的整体介绍。谢谢。

## 6. 简历每条 bullet 的口语解释
### Bullet 1：RK3588/16GB 端侧部署验证系统和 C++20 runtime
> **面试官提问**：这是不是生产项目？四个线程分别是什么？为什么写 C++20？
>

+ **30 秒口语解释**：  
这并不是一个真实的工厂上线项目，而是基于公开数据集的端侧部署工程验证系统。Edge 运行时采用 C++20 编写，分为图像采集、门控过滤、模型推理和多部分上传四个独立线程。由于我们需要在空队列等待时利用 `stop_token` 和条件变量实现平滑的协作式退出，因此采用 C++20 标准。
+ **2 分钟口语解释**：  
我们做这个端侧运行时的核心目标，是解决“端侧采集、门控过滤、模型推理和网络上传”这四个耗时完全不同的模块如何在同一个芯片上稳定共存的问题。为此，我设计了基于 C++20 的四线程 staged pipeline，四个线程依次为：T1 图像采集、T2 EfficientAD 异常过滤、T3 主模型推理和 T4 网络上传，线程之间使用三个 BoundedQueue（采集队列、过滤队列、推理队列）进行数据流转。  
队列满时会采用 drop-oldest 策略丢弃最旧帧，以防止后面的慢推理把整条流水线卡死，优先保当前画面；而在空队列等待时，消费者采用 stop-aware wait 条件变量阻塞，一旦主线程发出停止信号，可以通过 stop_token 唤醒退出，并优雅释放 RKNN/RKLLM 内存资源。上传线程完全解耦，防止 HTTP 网络延迟波及前面的采集。  
不过作为工程验证系统，我们目前只实现了这套协作退出的 BoundedQueue 机制，队列并没有像生产级产品那样提供 `close()`、`shutdown()` 或者 `drain()` 等复杂的生命周期 API，这也是我们的工程边界所在。

### Bullet 2：大模型异步增强链路验证
> **面试官提问**：这个链路证明了什么？36/36 是不是准确率？VLM 延迟怎么样？
>

+ **30 秒口语解释**：  
大模型异步增强链路验证，主要是证明了“EfficientAD 门控 + FastSAM 候选框 + Qwen3-VL 大模型”这一整套多模型串联在板端是能够长稳运行的。测试中我们跑了 30 分钟，取得了 36 次成功解析的 JSON completions。但 36 次解析成功只是格式可消费，并不是缺陷分类的准确率，大模型平均耗时在 15 秒左右。
+ **2 分钟口语解释**：  
这套大模型验证方案的初衷，是验证边缘端是否具备对复杂工业缺陷进行结构化语义解释的能力。整个链路是这样的：T2 先运行 EfficientAD 作为异常门控筛选，如果判定异常，T3 运行 FastSAM 提取 bbox 候选框，然后调用本地部署的 Qwen3-VL 2B 模型的 W8A8 量化版，最终输出结构化的缺陷描述和建议。  
在长稳测试中，系统跑了 30 分钟，捕获了 366 张图，通过门控过滤生成了 36 次 completions。0 crash 且 36 次 completions 全部成功通过了后端 JSON schema 解析。这验证了我们 C++ 进程生命周期与 RKLLM 推理的稳定性。  
但通过数据我们也发现，VLM 总的平均耗时高达 15 秒左右。在工业实时现场，秒级的耗时意味着它绝对不能当作同步检测器来使用。这就是它带给我们的最大设计指导：大模型在端侧只能用作异步增强，实时定位必须交给轻量级的 YOLOv8 定位器。

### Bullet 3：端侧量化和兼容性诊断
> **面试官提问**：FastSAM 量化失败根因是什么？LoRA 量化后为什么会崩？
>

+ **30 秒口语解释**：  
这一块主要是我们在多模型转换中沉淀出的三个真实诊断案例。第一个是 FastSAM INT8 量化后 output0 scale 偏大导致反量化置信度阈值过滤后没有候选框，我们fallback到了 FP16；第二个是 EfficientAD 因 AUROC 指标较低降级为门控；第三个是 LoRA 微调大模型在 W8A8 量化后发生的性能坍塌，目前LoRA 不进主线，只作为失败复盘。
+ **2 分钟口语解释**：  
端侧模型部署最容易犯的错误是“以为转出模型文件就大功告成”。我用三个案例证明了即使编译成功，数值和指标也可能失效。  
第一个是 FastSAM：它的检测头 output0 同时输出 bbox 坐标和 confidence。per-tensor 量化后，scale 动态范围被坐标大值主导，偏大到了 2.82。代入公式反量化发现，一个量化级距就是 2.82，已完全越过了置信度 `[0,1]` 的有效区间，导致后处理直接拿不到候选框。为此我们 fallback 到了 FP16，只做 bbox proposal。  
第二个是 EfficientAD：实测 AUROC 平均只有 0.5320，无法做最终的缺陷定位，因此我果断调整了其定位，将其降级为只筛选异常的异常门控。  
第三个是 LoRA：PC 端仿真测试细粒度缺陷识别率有 51.8%，但到板端量化模型后识别率为 0/7。这表明 W8A8 量化会直接吞掉微调出来的细小 delta 增量。  
这些问题都不是调参能解决的，它促使我们把模型职责和 fallback 降级做成了明确的架构隔离。

### Bullet 4：YOLOv8n 定位器 CPU 降级运行验证
> **面试官提问**：为什么不是 RKNN？187.7ms 算慢吗？数据范围多大？
>

+ **30 秒口语解释**：  
在同步定位路径中，我们训练了只覆盖 metal_nut 和 cable 两类缺陷的 YOLOv8n 定位器。虽然我们尝试过转换 RKNN，但由于 class score 通道在板端的一致性校验未通过，相关性接近零，所以最终做出了 ORT CPU 降级运行的正确性决策。在长稳测试中它跑了 2082 帧，模型推理平均在 187.7ms。
+ **2 分钟口语解释**：  
为了实现低延迟同步检测，我们定制了 YOLOv8n 定位模型，针对 MVTec 的 metal_nut 和 cable 两类、12 个缺陷子集进行训练，mAP50 达到 0.593。虽然转换 `.rknn` 能够跑通 smoke 吞吐测试，但在一致性回查中发现 class score channels 相关性几乎为零，模型输出的类别是错的。  
在工程设计上，我遵循正确性优先原则，宁愿阻碍 NPU 的推理耗时，也不能在主公路上跑错误的 NPU 输出。因此我设计了 ONNX Runtime CPU fallback 降级，在 extended soak 测试中持续运行 27m27s、处理 2082 帧无崩溃，单步推理平均 187.7ms。这个延迟表现成功把推理从秒级拉回了百毫秒级。  
但我也必须强调，这 187.7ms 只是 YOLO 在 ORT CPU 上的单步耗时，不是端到端延迟，我们的数据范围目前也仅限于这两类缺陷子集。

### Bullet 5：端云闭环与可观测性
> **面试官提问**：后端和前端怎么联动？345 项契约测试保什么？
>

+ **30 秒口语解释**：  
Edge 用 HTTP POST 二进制 multipart 发送图片和元数据 JSON；FastAPI 后端校验 schema 和 bbox 越界后写入 SQLite 并通过 WebSocket 广播；Next.js 前端则负责来源标定叠加和 Chrome Trace timing 性能观测。后端 contract tests 共通过 345 项，用于保障数据契约的稳定性。
+ **2 分钟口语解释**：  
我们做端云闭环和可观测性，核心价值是防止数据的错误消费和指标混淆。在多模型混合运行下，如果前端分不清一个框到底是 YOLO 检出来的、大模型推荐的候选框、还是 fallback 的空占位框，整个缺陷追踪就会失真。  
所以我们统一了数据契约：Edge 端将图片二进制和 meta JSON 分 part 进行 multipart upload，避免 Base64 膨胀；FastAPI 负责字段 schema、JPEG size 限制和 bbox 越界逻辑的 contract 验证（目前 345 项自动化契约测试全部通过），写入 SQLite WAL 本地库后通过 WebSocket 广播；前端 FrameInspector 会明确标示 BBox 的 source（YOLO 还是 VLM 候选框），ProfilePage 则支持直接导出 Chrome Trace，定位各 stage 延迟。  
需要说明的是，当前的 SQLite 写入和 WebSocket broadcast 均在单机进程内验证，不能等同于分布式高并发的生产集群；快照数据也只是精心准备的 demo 展示，不作为长稳运行报告。

## 7. 通用原理 / 八股 warmup 口语专区（audited B01-B20）
### B01. 你简历里写 `std::jthread`，那你到底是 C++17 还是 C++20？
+ **15 秒答**：  
我们项目采用的是 C++20 标准。Edge 运行时是用 `std::jthread` 启动了四个固定职责的 worker 线程。
+ **60 秒答**：  
在边缘端 pipeline 中，我们需要平滑协作退出和避免线程意外析构。C++20 的 `std::jthread` 相较于 `std::thread` 最大的优势是内置了 RAII 生命周期管理和 `std::stop_token` 协作取消机制。在 jthread 析构时会自动请求停止并 join。  
在项目中，我们的 T2/T3/T4 线程的 main loop 都接收了 `stop_token`，在条件变量等待时使用 stop-aware wait。一旦进程触发退出（如捕获 SIGINT），jthread 自动下发 stop 请求，阻塞中的队列条件变量会被立刻唤醒并优雅退出，防止了 RKNN/RKLLM native 句柄出现内存泄漏。
+ **项目映射**：C04 / `edge/src/main.cpp`
+ **防守提示**：不要写 C++17，B01 本质是语言标准检查。

### B02. 你这个四线程是线程池吗？
+ **15 秒答**：  
不是线程池，它是固定的 staged pipeline，包含采集、门控、推理和上传四个阶段任务。
+ **60 秒答**：  
线程池适用于处理同质、并发的小任务；而我们的工业视觉链路不同阶段的耗时和算力需求完全不同。例如大模型推理需要秒级，上传受网络波动影响，而图像采集是微秒级。如果丢进同一个线程池，容易发生慢任务死锁和无界积压。  
因此我们使用 BoundedQueue 将四个独立线程串成 staged 管道。这种结构能清晰地为每一个阶段设置独立的背压队列，比如 Q2 过滤队列容量只设为 2，大模型一旦推理慢就会迅速向上传递背压，强制 T2/T1 限制采集节奏或触发丢弃，防止内存积压。
+ **项目映射**：C04 / `edge/include/edge/common/bounded_queue.hpp`
+ **防守提示**：不要说这是通用并发线程池。

### B03. 队列空的时候 worker 在干嘛？会不会 while 轮询烧 CPU？
+ **15 秒答**：  
消费者线程不会在 `while(true)` 里空转轮询，而是通过条件变量阻塞休眠，并在退出信号来临时协作退出。
+ **60 秒答**：  
在我们的 `BoundedQueue::pop(stop_token)` 内部，如果没有可消费的元素，消费者线程会进入条件变量的 wait 状态休眠，让出 CPU 资源。这里我们使用的是 C++20 的 `condition_variable_any`，调用 `wait` 时传入了 `stop_token` 和等待谓词。  
当生产者 `push` 元素并发送 `notify_one` 时，或者系统触发退出、`stop_token` 变更为 stop 状态时，休眠的线程会被瞬间唤醒。如果是因为 stop 退出，pop 会直接返回 `std::nullopt`，worker 线程 break 出主循环，完成优雅退出。
+ **项目映射**：Code Delta: BoundedQueue::pop
+ **防守提示**：大方承认当前有界队列没有实现 close、shutdown 或 drain 等生命周期控制方法。

### B04. drop-oldest 会不会把缺陷帧丢掉？
+ **15 秒答**：  
确实会有丢缺陷帧的风险。这是我们系统在实时预览和高延迟慢推理之间做出的工程取舍，我不会把它包装成生产级 SLA 承诺。
+ **60 秒答**：  
在有界背压队列里，当队列满了，我们必须在“阻塞上游、丢弃最新帧、丢弃最旧帧”之间做出决策。在工业视觉实时展示场景中，历史积压的旧帧即使检测出来，对当前的系统状态而言其价值也大打折扣，阻塞上游更会带来难以接受的同步延迟。  
因此，项目选择 `drop_oldest` 来优先保证当前消费到的是最新采集的图像，并通过 QueueStats 将 drop 计数暴露给可观测后端。如果面试官问如何避免丢帧，我会在生产级演进中提出引入离线 spool 暂存或者增大并发线程，但在此验证系统里，drop 发生是实时性取舍的客观事实。
+ **项目映射**：C04 / QueueStats
+ **防守提示**：不要声称队列在任何情况下都“绝对不丢帧”。

### B05. RAII 管 RKNN/RKLLM 句柄，失败路径真的不会泄漏吗？
+ **15 秒答**：  
我们通过 RAII 对 RKNN 和 RKLLM 的原生句柄进行了智能包装，但在特定的第三方例外路径中目前仍需人工释放。
+ **60 秒答**：  
在板端 C++ 运行时中，由于模型加载失败或运行时异常随时可能抛出，如果依靠人工在每一条 exit path 上释放 native 指针和 context 句柄，很容易导致资源泄露。我们设计了 `UniqueRknnCtx` 和 `UniqueRkllmHandle` 等 RAII 包装类，保证生命周期绑定到 C++ 对象上，无论何种路径退出，析构函数均会自动调用底层的 release 释放 handle。  
但由于有些大模型 runner 代码中，我们直接持有了底层的 LLMHandle，依然存在极少数未能完全统一包装的例外路径。
+ **项目映射**：C05 / `Qwen3VLRunner`
+ **防守提示**：承认部分大模型 runner 目前依然存留例外释放路径，体现工程客观性。

### B06. ONNX/RKNN 转换成功算部署成功吗？
+ **15 秒答**：  
不算。转换出文件只是迈出了第一步。部署验收必须经过导出、运行、数值一致性以及任务指标可用性这四层检验。
+ **60 秒答**：  
在部署实践中，我常画一幅四层框架图：第一层 Export 导出；第二层 Runtime 真机加载；第三层 Numeric Consistency 数值一致性对齐；第四层 Task Metric 业务指标可用。  
比如我们的 YOLOv8n，在 PC 端 Toolkit 转换并导出 `.rknn` 成功（通过第一、二层），但真机回查发现 classification scores 和 ONNX 相比相关性近乎为零，卡在第三层；又如 FastSAM 虽然能跑通，但 INT8 量化误差吞掉了置信度，卡在第四层。所以只拿转换成果去论证部署成功是极不可信的。
+ **项目映射**：C06/C08/C17
+ **防守提示**：坚守四层框架，大方说明项目中有 blocked 路径。

### B07. RKNN Toolkit 和板端 RKNN Runtime 你在哪一步验证？
+ **15 秒答**：  
我们在 PC 端用 Toolkit 负责量化与导出；在 RK3588 真机上加载 Runtime 库进行 smoke 与长稳测试。
+ **60 秒答**：  
PC 端的 `rknn-toolkit2` 工具链只负责模型结构裁剪、量化参数计算和 `.rknn` 二进制导出。这只能在仿真或 Toolkit simulator 层面做初步的一致性回归。  
真正的运行验证必须将 `.rknn` 文件拷到 RK3588 真机上，调用 RKNN Runtime C/C++ API 或者 RKLLM runtime 进行加载和真机 `rknn_run`。我们在开发中，第一步在 PC 验证导出，第二步在板端部署 smoke 验证算子兼容，第三步在板端做 extended soak 长稳来捕捉内存和耗时抖动。
+ **项目映射**：C15/C17
+ **防守提示**：不要把 PC 仿真指标和板端实测指标混在一起。

### B08. numeric consistency blocked 具体是哪里不一致？
+ **15 秒答**：  
主要是不一致表现在 RKNN 真机输出的类别置信度和参考 ONNX 模型输出的相关性接近为零。
+ **60 秒答**：  
数值一致性不能看大概相似，而是要固定相同的正样本和负样本输入，比对二者的激活范围、输出 shape 和数值相关系数。  
在 YOLO 的排障中，我们发现 NPU 输出的分类置信度通道数据，和 PyTorch 浮点模型输出相关性几乎归零。这意味着模型提取特征可能正常，但分类头发生了混淆。由于没有通过这层一致性检验，我们判断在 NPU 上运行会导致前端和后端消费到完全错误的分类指标，所以果断 blocked 并降级走 ORT CPU。
+ **项目映射**：C17
+ **防守提示**：不把 blocked 包装成通过，承认 YOLO RKNN 失败。

### B09. 你这个 INT8 是 PTQ 还是 QAT？为什么没坚持 INT8？
+ **15 秒答**：  
我们采用的是 PTQ（训练后量化）。FastSAM 没坚持 INT8 是因为置信度通道量化误差过大导致候选坍塌，而项目目前未进行 QAT 验证。
+ **60 秒答**：  
PTQ 通过校准集快速映射浮点到整型，简单高效，但遇到具有激活动态异常值（outlier）的层时精度容易雪崩。QAT 虽能保精度，但需要重新微调训练模型。  
由于 FastSAM 包含多任务检测头，置信度通道和坐标通道共享了 per-tensor 量化尺度，其 scale 被大坐标拉大到 2.82，直接压扁了 confidence 的小范围信号分辨率，后处理候选框全被过滤成了 0。在正确性优先的前提下，我们主动 fallback 到了 FP16，没有盲目坚持 INT8，并将 QAT 列为未来的优化方向。
+ **项目映射**：C08
+ **防守提示**：绝不说自己做了 QAT。

### B10. scale / zero point 工具会自动处理，为什么要手算？
+ **15 秒答**：  
因为端侧输出反量化后，其数值分辨率被量化 scale 决定。手算可以让我们在后处理失效时诊断出是动态范围问题。
+ **60 秒答**：  
反量化公式是 `float = (q - zp) * scale`。虽然量化工具在转换模型时会自动估计 scale 和 zero point，但它无法替我们预知后处理阈值的合理性。  
比如 FastSAM INT8 导出的 `zp=-119, scale=2.82`。手算代入公式，如果量化值 q 发生 1 个级距的变化，对应的浮点浮动就高达 2.82。然而我们的置信度 conf 有效区间在 0 到 1 之间。也就是说，一个最小的量化刻度，就已经远远超过了置信度的有效动态范围。结果就是 confidence 反量化后直接发生了截断，阈值 `conf>0.25` 过滤后 raw candidates 全部是零，大模型和前端根本消费不到候选框。如果只看工具日志而不用公式诊断，根本找不出后处理失效的原因。
+ **项目映射**：C08
+ **防守提示**：不要含糊，直接给公式和手算数据。

### B11. per-tensor 和 per-channel 跟你这个 confidence 坍塌有什么关系？
+ **15 秒答**：  
per-tensor 共用一个 scale，异常值拉大 scale 会牺牲置信度这种小信号的分辨率；per-channel 独立 scale 则能保住这些通道。
+ **60 秒答**：  
在多任务检测模型如 YOLO/FastSAM 中，输出张量同一维度包含了坐标、分类和置信度等多类信息，其数值动态范围可能相差几个数量级。如果采用 per-tensor 量化，全量共用一个 scale 导致尺度极度偏向大范围的坐标，小范围的置信度信号被极粗的量化桶“压平”了。  
per-channel 可以对不同的输出通道（如置信度通道）独立计算 scale/zp，从而防止分辨率被大通道掠夺。但在我们的板端转换工具中目前只跑通了 per-tensor，所以才暴露了 confidence 坍塌的现象。
+ **项目映射**：C08
+ **防守提示**：承认项目目前未能成功在板端调通 per-channel 修复方案。

### B12. 校准集怎么选？覆盖不足会怎样？
+ **15 秒答**：  
校准集应选择覆盖模型运行分布的代表性样本；覆盖不足会导致 PTQ 量化阶段激活值截断和 scale 漂移。
+ **60 秒答**：  
校准集的作用是收集模型前向传播时的激活值动态范围。如果校准集选取的样本分布单一，比如全是某种纯色好图，那量化工具就会低估真实缺陷样本中的动态范围异常值，导致在线推理时出现饱和截断。  
在 EfficientAD-S PTQ 中，我们使用包含 good 样本的校准集进行 range 校验，YOLO 训练则用了 185 张图像。如果校准集覆盖不足，直接会导致真机量化精度发生崖式下跌（cliff）。
+ **项目映射**：C06/C16
+ **防守提示**：不编造量化校准集的详细构成数据，如没看对应 python 脚本，仅报数据集规模。

### B13. FastSAM 是 segmentation，为什么不说做了 mask segmentation？
+ **15 秒答**：  
因为当前项目中 FastSAM 只完成了候选框提取（bbox proposal），最底层的原型掩码解码（mask decode）代码未实现。
+ **60 秒答**：  
FastSAM 模型确实支持完整的实例分割，包含 output0 的候选框检测和 output1 的 prototype mask 掩码。但从工程证据出发，我们在 C++ 端只对接了 output0 的 bbox proposal 生成，并做了对应的 bbox 框清洗。  
由于 output1 的掩码后处理解码在当前 Edge runtime 中依然处于 TODO 状态，如果我们在面试中包装为“实现了完整分割”，就会在代码层面被打穿。因此我们坚持实事求是，只称其为 bbox proposal 生成器。
+ **项目映射**：C08/C09
+ **防守提示**：不要混淆“模型具有的能力”和“项目实际落地的能力”。

### B14. mAP、AUROC、json_parse_ok 谁衡量模型准不准？
+ **15 秒答**：  
mAP 衡量检测框和分类的质量，AUROC 衡量异常门控得分的区分度，json_parse_ok 仅仅代表 API 的数据格式解析成功。
+ **60 秒答**：  
面试中必须把这三个指标严格区别开。json_parse_ok 是一个数据反序列化指标，不能用来掩盖检测错误。例如我们做 LoRA 微调，板端的 JSON 解析率达到 14/14（100%），但缺陷的细粒度识别 defect_type_exact 却是 0/7（完全错误）。  
对于目标检测（YOLO），我们看 mAP50（当前 0.593）；对于异常检测门控（EfficientAD），我们看 AUROC（当前 0.5320）。这三个维度缺一不可，绝不能混淆。
+ **项目映射**：C02/C12/C16
+ **防守提示**：不吹嘘 100% 准确率。

### B15. LoRA 的 rank、alpha、target modules 为什么这么配？
+ **15 秒答**：  
我们的 2B/4B 大模型均配置了 rank=32、alpha=32，打在 q/k/v/o 投影矩阵上，这是在等效 batch=8 下做公平性能对照。
+ **60 秒答**：  
LoRA 在冻结 base 权重的两旁训练低秩增量矩阵。其中，alpha 代表对增量权重的缩放因子（scaling = alpha/rank）。我们把 rank 和 alpha 都设为 32，可以让增量按 1.0 的比例直接作用于 base，避免了过大缩放导致的不稳定。  
之所以打在 attention 模块的 q/k/v/o，是因为缺陷诊断高度依赖自注意力通道对特征的局部融合，同时我们选择冻结了视觉塔（vision tower）和多模态 projector，以降低可训练参数规模，避免小数据集微调过拟合。
+ **项目映射**：标杆-B
+ **防守提示**：如果没在 yaml 中核实，不编造具体的 LR 或 epoch，大方承认这些微调参数主要是 PC 端仿真数据，板端已失效。

### B16. Qwen3-VL 慢，是慢在首 token、decode，还是总链路？
+ **15 秒答**：  
大模型推理耗时是端到端总延迟。我们需要将其拆分为 Prefill 首字时间（TTFT）和 Decode 逐字生成速度。
+ **60 秒答**：  
评估 VLM 耗时时不能粗放说慢。Qwen3-VL-2B 在 RK3588 真机上，其 TTFT（首字时间，包含图片特征提取与 embedding 拼接）平均需要 2.5 秒左右，生成阶段的 decodeTPS 大约为 9.46 tok/s。  
结合我们任务的提示词和输出，平均生成数十个 token。加上网络上传和后处理，端到端总时间（total latency avg）在 15.4 秒左右。由此可见，Prefill 的高算力消耗是其端侧运行的最大瓶颈，这也直接解释了为什么大模型方案无法在工业主链路上做同步实时推理。
+ **项目映射**：C03
+ **防守提示**：不能把 YOLO 187.7ms 的 CPU fallback 耗时混写到 VLM 性能中。

### B17. KV cache 跟你这个项目有什么关系？
+ **15 秒答**：  
它解释了 VLM 自回归生成中内存占用和延迟的来源。但在本项目中我们并没有修改或做 KV cache 底层优化。
+ **60 秒答**：  
大模型自回归 decode 时，每生成一个新 token 都需要和所有历史 token 做注意力计算。KV cache 用空间换时间，把历史 token 的 Key 和 Value 向量缓存进运行内存，防止每一步都做 $ O(N) $ 重复计算。  
但随着文本变长，KV cache 会迅速榨干板端的内存带宽，并带来推理延迟的线性增长。这解释了为什么 Qwen 耗时是秒级，也证明了异步旁路设计的合理性。在此项目中，我们主要用它来做多模态推理的瓶颈机解释，未完成代码级 KV cache 的特定优化。
+ **项目映射**：C03/C10
+ **防守提示**：不要说自己写了 KV cache 优化代码。

### B18. Edge 为什么要用 multipart？Base64 不是更简单吗？
+ **15 秒答**：  
multipart 能够在 HTTP 协议中实现文件二进制和元数据分段独立传输，避开了 Base64 带来的 33% 体积膨胀和额外的编解码开销。
+ **60 秒答**：  
Base64 编码会把三字节的二进制转化为四个可读字符，使得网络传输的图片数据无端增大 1/3 的带宽压力，并在端侧引入不必要的编解码计算。  
我们采用 `multipart/form-data`，通过 multipart API 独立封包：第一部分是二进制 image 流，第二部分是 meta JSON 文本。后端 FastAPI 接收时可以直接分流，在内存中直接流式读取 JPEG size 做限制（<=2MB），并用 Pydantic 对 meta 校验。这无论在网络开销还是接口契约设计上都更加优雅。
+ **项目映射**：C21/C23
+ **防守提示**：后端限制是 JPEG <=2MB，注意与文档版本 v1.3 的 payload 区分开。

### B19. WebSocket 为什么不是 Edge 直接推前端？
+ **15 秒答**：  
Edge 只做同步 HTTP 契约上传以保持精简；WebSocket 仅置于后端与前端之间，专注于可观测时序广播，明确系统边界。
+ **60 秒答**：  
如果让边缘端（Edge）直接和前端建立 WebSocket，会让 RK3588 板端不得不去处理前端 UI 的连接生命周期、心跳保活和断线重连。这会严重污染实时检测线程的稳定性。  
我们将 Edge 定位为只进同步 HTTP 上传的数据生产者。上传到后端（FastAPI）校验并落库 SQLite 后，由后端的进程内 WebSocket Manager 统一向订阅的前端广播最新的 BBox 和 Enrichment 信息。前端与 Edge 无直接连接，这极大保证了端侧的资源隔离与系统安全性。
+ **项目映射**：C21/C23/C24
+ **防守提示**：不要说 Edge 开了 WebSocket。

### B20. Backend 345 tests passed 能说明什么？能说明模型准吗？
+ **15 秒答**：  
不能，它只说明端云协同的数据结构、字段定义和文件上传等工程契约是合法的，不能代表模型的预测准确率。
+ **60 秒答**：  
这 345 项契约测试是我们为了防止系统集成破损而设计的。它利用 FastAPI TestClient 自动化测试了 multipart 图片上传、schema 版本对齐、bbox 越界检测、WebSocket 广播分包等接口稳定性。  
契约测试能保证前端在消费 YOLO 或 VLM 输出的数据时不会因为类型漂移而破损报错，但模型的预测质量（如 YOLO 的 mAP 或 EfficientAD 的 AUROC）只能由算法指标来评估。把接口契约的通过率包装成模型的准确率，是极不诚实的口径错误。
+ **项目映射**：C22/C24
+ **防守提示**：不要把契约测试通过当成算法准确率。

但我做这个项目并不是为了跑一个简单的 notebook demo，而是想在真机上验证边缘部署的全链路工程可行性。我们实际完成的成果包括：板端基于 C++20 设计的四线程流水线、大模型异步增强链路的 30 分钟长稳 soak 运行、以及 YOLO ORT CPU 定位器的 2000 多帧长稳测试。在转换和部署中，我们没有只写成功部分，而是如实诊断并复盘了 FastSAM INT8 的置信度坍塌、LoRA 在 W8A8 量化下的 cliff、以及 YOLO NPU 一致性校验失败等部署阻碍。所以从工程完整度上，它是一个非常扎实的端侧部署验证和量化排障工程。

### Q2. 为什么端云分离？
+ **30 秒自然回答**：  
端云分离的核心决策是为了隔离端侧资源，保障同步检测的实时性。板端 Edge 专注推理背压和二进制 multipart 契约上传，Web 后端（FastAPI）承载数据契约校验与 SQLite 持久化，前端（Next.js）只做结果标定和 Chrome Trace 可观测性展示，使板端运行足够清爽。
+ **2 分钟自然回答**：  
在系统设计上，我最担心的是板端因为承载了非推理相关的复杂业务而导致崩溃。如果让 Edge 直接处理网页连接、时序数据大容量持久化或者 WebSocket 保活，推理线程极易被网络抖动或者 UI 状态卡住。  
因此我们做出了端云解耦决策：Edge 端只保留 core C++ 推理，通过 `http_client` 发送 multipart 二进制 POST 请求，抛出数据后即不再承担任何连接管理。FastAPI 接收到数据，检验 schema 无误后再写入 SQLite 并做 WebSocket 广播，Next.js 前端再从后端订阅广播数据进行时序绘制和 Trace 导出。这不仅保证了端侧推理线程的纯粹性，也保证了数据接口的单一和安全。
+ `[💡 内部提示：严守 C21/C23/C24 架构边界]`
    - _Edge 端没有 WebSocket 监听，无数据库，只做 HTTP POST 上传。_

### Q3. 为什么双路径？
+ **30 秒自然回答**：  
双路径设计是为了把“大模型的视觉解释能力”和“定位器的实时检测能力”在架构上进行解耦。大模型可以做结构化缺陷解释，但延迟高达 15 秒；轻量 YOLO 定位快，延迟只有百毫秒。我们不是优化了同一个模型，而是用双路径分层处理。
+ **2 分钟自然回答**：  
当面临复杂缺陷检测时，单一模型很难同时满足“秒级实时定位”和“丰富的语义解释”。我们的第一条大模型异步增强链路，虽然实现了 FastSAM 与 Qwen3-VL 2B 的完整对接，能够输出丰富的 JSON 异常描述，但 15 秒的耗时让它根本不可能去卡同步定位主链路。  
为了解决这个延迟死穴，我们把架构调整为同步 localizer 定位和异步大模型解释双路径。同步定位交给輕量 YOLOv8n 本地推理，将单步推理压缩到 187ms，第一时间反馈设备状态；而大模型路径后移到异步增强，由 canonical field guard 严格限制大模型的写入范围。这样我们用两条路线的取舍，既保住了检测的时效性，又保留了多模态大模型的二次解释价值。
+ `[💡 内部提示：严守 C18 双路径延迟差异]`
    - _不能说两条路径是“同一个模型的优化对比”，YOLO 是定位，VLM 是解释。_

### Q8. YOLO RKNN 为什么 blocked？

+ **2 分钟自然回答**：  
在模型转换阶段，我们不仅要让 `.rknn` 文件能被加载，还要对齐它量化后的数值动态分布。我们遇到的问题是：YOLOv8n-seg 输出的 class score 多个通道在板端运行时和 PC 端的浮点参考输出无法对齐，分类相关系数接近于零。  
我们排查了标准转换路径和 airockchip 官方针对多输出头的转换方式，由于量化 scale 对齐以及前处理 RGB/BGR 一致性在 Toolkit 转换时依然存在阻碍，导致后处理概率完全混淆。为了防止主链路给出错误的类别提示，我们将 YOLO RKNN 标记为阻碍（blocked），使用 Python subprocess JSON-line 方式调起 `scripts/phase10/ort_localizer.py`，降级为 ORT CPU 主线。这代表我们在量化转换上遇到了需要后续精细调优的一致性卡点。
+ `[💡 内部提示：对齐标杆-A 精度诊断]`
    - _说明自己定位到了 class score 动态范围混淆，而不是单纯不会用 Toolkit，展示技术深度。_

### Q9. FastSAM INT8 为什么失败？
+ **30 秒自然回答**：  
FastSAM INT8 失败是因为采用了 per-tensor 量化后，其 output0 包含了检测坐标和大动态范围值，量化 scale 偏大到了 2.82。这直接把置信度通道（在 0 到 1 之间）的量化分辨率“压扁”了，导致反量化后置信度非 0 即远大于 1，`conf>0.25` 后候选框全被过滤为了 0。
+ **2 分钟自然回答**：  
这个案例很好地展示了端侧 PTQ 量化中“转换能跑通、后处理失效”的现象。FastSAM-s 导出的 output0 张量形状是 `[1,37,8400]`，因为采用了 per-tensor 量化，整个张量共用了一组 scale 和 zero-point。  
实查量化属性发现其 `zp=-119, scale=2.82`。带入反量化公式：当 q 值发生一个量化步长，浮点变动就高达 2.82。可是，置信度 confidence 的有效范围本在 0 到 1 之间。也就是说，一个最小的量化刻度，就已经远远超过了置信度的有效动态范围。结果就是 confidence 反量化后直接发生了截断，阈值 `conf>0.25` 过滤后 raw candidates 占绝对数的零，大模型和前端根本消费不到候选框。为此我们不得不将 FastSAM fallback 到 FP16 模式下运行，这也促使我们今后在类似模型上要优先考虑 per-channel 或者混合量化。
+ `[💡 内部提示：严守 C08 FastSAM INT8 根因]`
    - _这里不要编造已经解决了 INT8 问题，承认当前是用 FP16 fallback 避开它。_

### Q10. LoRA W8A8 cliff 是什么？
+ **30 秒自然回答**：  
量化悬崖是指大模型做 LoRA 细粒度微调后，PC 端 bf16 仿真测试准确率不错，但一转成板端 W8A8 量化模型后，缺陷细粒度识别性能崩溃，相关指标掉到了 0/7。这表明 W8A8 低比特量化会吞掉微调出来的细小 delta 增量，使语义理解失效。
+ **2 分钟自然回答**：  
我们在 PC 端用 bf16 跑仿真时，LoRA 2B 微调模型在 defect_type_exact 细粒度缺陷类型上的表现是 212/409，差不多 51.8% 的识别率；但同样的 LoRA 模型转换到板端跑 W8A8 低比特模型，测试 n=14 的 defect subset 时，虽然 JSON 100% 解析成功，但细粒度准确率掉到了 0/7。  
这个量化悬崖的机理在于：LoRA 训练出来的 delta 矩阵是一组极微弱的权重增量（低秩微调特性）。当大模型进行整体 W8A8 低比特 PTQ 量化时，量化量级比较粗糙，这些细微的权重增量在量化映射后被当成了噪声或者被截断舍入掉了，导致微调出来的细粒度缺陷分类特征丢失。这也告诉我们，在端侧小显存场景下，LoRA 搭配 PTQ 并不是万能药，我们必须引入更高精度或者量化感知微调（QAT）才能稳住细粒度语义。
+ `[💡 内部提示：严守 C12 LoRA 量化 cliff]`
    - _承认 LoRA 目前在端侧量化下性能失效，不将其吹捧为已在 RK3588 成功落地的微调方案。_

### Q11. BoundedQueue 为什么 drop-oldest？
+ **30 秒自然回答**：  
在实时缺陷预览中，过期的图像帧对当前的工业监测没有实际价值，如果队列积压，我们必须丢弃旧数据。drop-oldest 能保证下游消费者（如 YOLO 或大模型）在有压力时拿到的依然是当前采集到的最新帧，同时避免了内存的无限积压。
+ **2 分钟自然回答**：  
当 Edge runtime 面临下游慢推理（比如大模型单次推理 15 秒）时，如果上游采集保持高频，很容易发生内存积压。我们的队列 Q1、Q2、Q3 容量设为 4、2、4，都是有界队列。  
如果采用普通的 block 阻塞策略，上游采集线程会被卡死，前端看到的会是几分钟前的历史延迟图像；如果采用 drop-newest，最新的帧进不去，大模型处理的永远是积压 of 旧数据。因此 `drop_oldest` 是对实时性的折中选择，队列满时在 `push` 端自动 `pop_front()` 丢弃最老的一帧，并递增 QueueStats 中的丢失计数。在大模型旁路推理测试中，drop 计数为 0 只是说明当前配置负载正常，并不代表在极端压力下不会丢帧。它是一个保住系统最新状态和限制内存开销的背压设计。
+ `[💡 内部提示：严守 C04 BoundedQueue 退出边界]`
    - _承认队列在遇到高频吞吐时必然会发生 drop，大方解释这是实时性取舍。_

### Q12. std::jthread / stop_token 协作退出怎么实现？
+ **15 秒答**：  
四个任务线程都由 `std::jthread` 启动，主循环中持续检查 `stop_token` 是否被取消。
+ **60 秒答**：  
在 Edge 的主线程中，由于各 worker 线程可能在 BoundedQueue 空队列上被 `wait` 条件变量挂起，如果强制 kill 线程会导致模型资源未能安全释放。我们使用 C++20 的协作退出机制：  
每个线程的 lambda 函数都接收了 `std::stop_token st`。队列的 `pop` 接口封装了条件变量的可中断等待：`cv.wait(lock, st, predicate)`。当主线程调用 jthread 析构或者主动下发 stop 信号时，`st.stop_requested()` 变真，被挂起的条件变量被唤醒，pop 返回 `std::nullopt`。worker 检测到后 break 退出循环，在析构中平滑清理 NPU 句柄，从而实现四个线程的安全解耦和协作退出。
+ **项目映射**：`edge/src/main.cpp`
+ **防守提示**：不要把这个 jthread 退出硬套写成生产级的独立进程管理器，它只是多线程优雅退出机制。

### Q13. EfficientAD 为什么只做 gate？
+ **30 秒自然回答**：  
因为在前期的数据集测评中，EfficientAD-S 的 raw_score 异常分数平均 AUROC 只有 0.5320，这个精度用来做最终定位和缺陷判决会带来严重的漏检。但它可以作为一个低算力耗时的门控，用来快速拦截大量正常样本，拦截不需要走慢大模型推理的帧。
+ **2 分钟自然回答**：  
EfficientAD 理论上可以输出缺陷的热力图和分数，作为最后的检测器。但我们在 MVTec 的 15 类图像、1725 张图片的校准测试中发现，其 raw_score 均值 AUROC 只有 0.5320，map_mean 只有 0.4561。这个异常检测的表现接近随机猜测，如果强行让它当主检测器，系统几乎不可用。

+ `[💡 内部提示：严守 C06 EfficientAD AUROC 边界]`
    - _承认 0.5320 的低精度表现，不把其门控降级粉饰为高精度的异常检测成果。_

### Q14. JSON parse 为什么不是准确率？

+ **2 分钟自然回答**：

+ `[💡 内部提示：严守 C12 LoRA 语义指标]`
    - _警惕面试官深挖 36/36，大方说明这只是 JSON 格式解析率，不等同于分类准确率。_

### Q16. Backend contract 怎么保证？
+ **30 秒自然回答**：  
我们通过 FastAPI 在接口处对 Edge 的 multipart payload 进行了强约束校验。检查其 image part、meta JSON 格式、`schema_version`、缺陷 bbox 是否越界，以及文件大小，通过 Pydantic 模型完成数据实体绑定；后端共运行了 345 项契约自动化测试来维护接口稳定。

在开发过程中，我们通过 345 项自动化 contract 契约测试用例，覆盖了元数据结构变动、缺失字段及格式错误上传等异常输入，保障了端到端通信通道的健壮性。

### Q17. Frontend 可观测性有什么价值？

## 9. 10 个反问转正答模板
### 1. 不是生产项目怎么说？
+ **正面结论**：承认这不是真实工厂上线项目，定位是 RK3588 多模型部署可行性验证工程。
+ **机理解释**：基于公开数据集（MVTec）能提供可复现的参考标准，有助于我们分层去诊断模型导出、Runtime 算子和数值相关性，而不被生产环境的噪声干扰。
+ **项目决策**：在板端跑通了 Edge jthread 流水线和两条长稳 soak，后端用 FastAPI 维护 345 项契约校验，前端通过 Chrome Trace 进行耗时分析。它是一个完整的可行性验证工程。
+ **安全收尾**：所以在口径上我不说生产级高可用或真实工厂部署。

### 2. RKNN 没用起来是不是说明项目没写完？
+ **正面结论**：YOLO NPU 部署 blocked 代表我们把数值正确性放在了第一位。
+ **机理解释**：在真机一致性校验中，发现 RKNN 与浮点 ONNX 的输出相关性几乎归零。在这种情况下如果强行用 NPU 推理，会产生完全错误的缺陷分类，整个系统失去意义。
+ **项目决策**：我们选择 correctness-first，果断 fallback 到了 ONNX Runtime CPU 降级主线，把延迟从秒级拉回了 187.7ms，成功完成了端云闭环的演示。
+ **安全收尾**：我们不能把 YOLO 跑在 CPU 上的降级运行说成是 NPU 加速成功。

### 3. LoRA 板端没跑通，写进简历是不是凑数？
+ **正面结论**：LoRA 板端失效是一个极具工程诊断价值的典型量化崖案例。
+ **机理解释**：LoRA 微调的是参数增量。大模型做 W8A8 低比特量化时，其量化刻度容易直接把这组微小的 delta 增量当成舍入噪声过滤掉，导致板端细粒度准确率崩为 0/7。
+ **项目决策**：我们没有只看 100% 的 JSON 解析成功，而是横向对比了 PC bf16 51.8% 精度与板端 W8A8 零进度的落差，并针对性设计了 canonical field guard，防止慢大模型在旁路修改主检测类别。
+ **安全收尾**：所以我不把它写成有效的端侧微调方案，只作为量化失败复盘。

### 4. 异步 VLM 长稳没跑完怎么说？
+ **正面结论**：异步 VLM 跑通了 smoke 和 guard，但 5d 长稳被 blocker 中止。
+ **机理解释**：5d soak 跑了 38 轮发生 halted，说明 runner 的数据可信度和大模型在长时推理下的长稳存在我们尚未定位的数据不一致阻碍。
+ **项目决策**：出于工程严谨度，我们必须将其标为阻碍，在简历里停在 smoke 和 guard 已验证的口径上，不隐瞒这 38 轮中止的缺陷。
+ **安全收尾**：不能宣称大模型异步增强已完全通过长稳。

### 5. FastSAM 没做分割算什么成果？
+ **正面结论**：FastSAM 在我们系统中承担的是 bbox proposal，不承担 mask 分割。
+ **机理解释**：多模态解释模型需要缺陷的候选框作为 ROI 区域输入，T3 在代码层面实现了 output0 候选框的提取和 L1-L5 清洗；而 output1 的实例掩码 decode 逻辑目前在代码中还是 TODO。
+ **项目决策**：INT8 置信度崩溃后，我们切到了 FP16 no-quant，只提供 proposal 框，不包装完整分割。
+ **安全收尾**：简历中只写 bbox proposal 候选生成，不说做了 mask 实例分割。

### 6. Anomaly Detection 只有 0.53 AUROC 为什么还要用？
+ **正面结论**：EfficientAD-S 的角色是负载削减 gate，不是最终决策判定器。
+ **机理解释**：0.5320 的均值 AUROC 确实太低，说明它对 15 类缺陷的定位精度不够。但作为前置门控，它可以通过好图阈值过滤掉大量正常的、不需要大模型解释的帧。
+ **项目决策**：T2 仅用作门控过滤，把后面 15 秒大模型推理的压力降下来，而缺陷的最终类别和框判定交给 YOLO主链路或者后续 VLM，用分层规避了 EfficientAD-S 本身 AUROC 的不足。
+ **安全收尾**：不说 EfficientAD-S 解决了缺陷判定。

### 7. 36/36 成功解析为什么不能说模型准？
+ **正面结论**：json_parse_ok 衡量结构可消费性，不衡量模型缺陷诊断准确率。
+ **机理解释**：JSON 能顺利反序列化，只能说明 prompt 和模型生成对齐了格式契约；要衡量模型好坏，必须回到 mAP和 AUROC等算法指标。
+ **项目决策**：LoRA 大模型 board JSON 解析 14/14 全通过，但真实 defect_type_exact 却是 0/7。我们坚持指标分区，不拿格式通过率混淆模型精度。
+ **安全收尾**：不能写 100% 检测准确率。

### 8. ORT CPU fallback 会不会太慢？
+ **正面结论**：ORT CPU fallback 是正确性优先下的稳定桥梁。
+ **机理解释**：在边缘端，一个给出完全错误分类结果的低延迟 NPU 模型，其危害性远远大于延迟 187.7ms 但输出完全可信的 CPU fallback 降级。
+ **项目决策**：我们选择优先保证数值正确性，让 YOLOv8n 在 ORT CPU 降级主链路上平稳运行，这成功帮助我们打通并测试了端云协同的契约校验和前端 Chrome Trace 性能诊断。
+ **安全收尾**：必须向面试官声明这 187.7ms 是 ORT CPU 的成绩，而非 NPU。

### 9. SQLite WAL 是不是太业余了？
+ **正面结论**：SQLite WAL 这里的定位是单机工程验证下的本地存储，不是云端高并发。
+ **机理解释**：我们用 SQLite 记录 1Hz 的遥测和缺陷时序，启用 WAL 模式可以避免读取和写入的锁冲突。对于单机演示而言，这已经足够轻量和高效。
+ **项目决策**：后端设计了 345 项契约自动化测试来防破损，前端用 WebSocket 实现时序广播，这验证了云端和前端逻辑。如果有高并发需求，只需把 SQLite 替换成集群数据库即可。
+ **安全收尾**：不说生产多实例数据库设计。

### 10. 快照和全量运行数据怎么区分？
+ **正面结论**：快照是精心挑选的展示和复盘样本，全量运行代表 soak 测试下的全局表现。
+ **机理解释**：为了保证演示可复现和稳定，前端需要一些 snapshot 数据来做 inspector 标定；但评估系统吞吐和 drop 时，必须回到 full run 全量报告。
+ **项目决策**：我们主动做口径划分，大模型 soak 全量处理 366 张图，前端快照只选取展示 20 条记录；YOLO 主线 soak 全量处理 2082 帧，前端展示 40 条快照。这防范了在面试中数字发生漂移。
+ **安全收尾**：不在汇报中把 snapshot 数据当作全局 soak 指标。

+ **T**：网络抖动或后端临时不可达时，绝对不能拖垮前面的 T1/T2/T3 实时推理线程。
+ **A**：我将上传任务分配到独立的 T4 worker 线程上，使用 BoundedQueue Q3 接收 T3 推理出的数据，T4 负责 HTTP 上传，失败仅记录计数，绝不反向 throw 异常回 T3/T2/T1。
+ **R**：在大模型路径长稳测试中虽然发生了 2 次网络 400 上传失败，但 Edge 端核心 jthread 零崩溃，且 BoundedQueue Q2 high watermark=2，成功实现了网络抖动和核心推理线程的资源隔离。
+ `[💡 内部提示：严守 C25 Upload 边界]`
    - _承认这只是线程解耦和失败计数，在当前 C++ 代码中并未实现完整的 upload_retry 成功上报。_

### 8. 快照与全量 soak 指标隔离
+ **S**：前端需要展示一部分缺陷记录做 FrameInspector 调试，这容易和长稳 soak 总帧数混淆。
+ **T**：在汇报和测试记录中，严防“用快照代替全量 soak 数据”的混淆发生。
+ **A**：我做出了明确的口径规范：大模型 soak 全量处理 366 张图，前端快照只选取展示 20 条记录；YOLO 主线 soak 全量处理 2082 帧，前端展示 40 条快照，前端 source 标明 `ort_yolov8n_cpu`。
+ **R**：成功保证了演示效果，同时在数据账本上彻底划清了界限，避免了在技术面试中数字发生漂移。
+ `[💡 内部提示：严守 C18/C22 隔离边界]`
    - _快照是精心挑选的 demo 数据，不能代表 soak 全量指标。_

### 9. 强契约校验保证接口零破损
+ **S**：HttpClient、FastAPI 后端和前端 Dashboard 频繁更改，可能引入字段类型不匹配。
+ **T**：保障 Edge 批量遥测上报和缺陷信息上传时的接口契约稳定性。
+ **A**：后端接口层校验 multipart 数据，强制 `schema_version` 为 `"v1"`，并利用 Pydantic 对 meta JSON 强绑定，校验 bbox 坐标值在 `[0,1]` 范围内。我们编写并跑通了 345 项契约测试覆盖异常输入。
+ **R**：实现了端云接口零破损，开发和前端运营中没有发生因字段漂移导致的崩溃。
+ `[💡 内部提示：严守 API 版本边界]`
    - _文档版本 v1.3，接口 payload schema 依然是 v1，区分清楚。_

### 10. BoundedQueue 有界背压限制内存积压
+ **S**：在 Edge 端，T3 推理耗时变长会导致系统内存发生暴涨。
+ **T**：需要在实时视觉检测中限制队列容量，尽早传递背压以保护内存。
+ **A**：我设计了有界队列，Q1=4、Q2=2、Q3=4。异常门控过滤后的 Q2 仅设为 2。当下游推理发生拥堵时，Q2 迅速填满，强行向前传递背压，迫使 T2 门控和 T1 采集减慢或者丢弃旧帧。
+ **R**：在大模型 15 秒极慢推理测试下，Edge 内存稳定在 3.2GB 左右，没有发生任何内存无限积压导致的 OOM。
+ `[💡 内部提示：严守 C04 BoundedQueue 退出边界]`
    - _承认当前 BoundedQueue 主要是协作退出机制，没有设计复杂的 _`close`_/_`drain`_。_

## 12. 最后背诵版
### 5 句话项目定位
1. 本项目是基于 MVTec AD 公开数据集的 RK3588 端侧多模型部署可行性验证工程，非工厂上线项目。
2. Edge 端是基于 C++20 实现的四线程背压流水线，FastAPI 后端提供 345 项契约验证，Next.js 前端负责来源标定与 timing 观测。
3. 方案一验证了大模型异步增强路径在板端的完备生命周期，但 VLM total 延迟平均在 15 秒左右，不适合充当同步主检测器。
